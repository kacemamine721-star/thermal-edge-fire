## Read this scope note first

This repository is **not** a flight-qualified autonomous system or a validated
uncooled LWIR microbolometer payload. It is a software pipeline targeting a
6U-class CubeSat architecture and evaluated with three Landsat-8 configurations:
the primary **C7+C6+C2** multispectral model, a **B10-only thermal control**,
and a C7+C6+C2+B10 hybrid.

The primary configuration is a **Landsat-8 OLI-like three-band model**:

```text
Pereira-3C = C7 (SWIR2) + C6 (SWIR1) + C2 (Blue)
```

It validates the onboard information-extraction chain, but its inputs are not
the output of an actual CubeSat flight sensor.

The B10-only model is an **evaluated thermal control experiment**. On the Pereira voting-mask test split it obtains F1 = 0.4119. This result
is **confounded by two factors that this benchmark does not separate**: (i) the
voting masks are generated by Landsat reflectance/SWIR algorithms, not thermal
algorithms, and (ii) Landsat-8 Band 10 has a native resolution of about 100 m
(distributed resampled to 30 m), so a small fire is diluted in a thermal pixel.
The B10 model finds large fires (event recall 1.00 above 100 px) and misses small
ones (0.05 for 1–5 px). The result therefore neither validates nor rejects a
future LWIR flight payload. Mission-level LWIR claims require thermal-native
labels or a carefully validated simulated-raw dataset, followed by
target-hardware measurements.

| --- | --- |
| 6U CubeSat edge-processing architecture | Proposed system architecture |
| Segmentation and information-product pipeline | Implemented software prototype |

## Problem and contribution

Earth-observation missions collect more imagery than can be transmitted during
short ground contacts. For wildfire response, the useful output is not every
pixel, it is a reliable, prioritized description of the events that matter.

Thermal-Edge-Fire addresses this as an **information-selection problem**:

```text
image frame → quality checks → segmentation → fire events → compact alert → priority queue
```

The project extends the segmentation work of the [Pereira ActiveFire](https://github.com/pereira-gha/activefire) benchmark
and the onboard prioritization pattern of [Chatar et al.](https://www.mdpi.com/2072-4292/16/10/1729#app1-remotesensing-16-01729) with:

- input-quality screening and optional transient scrubbing;
- a lightweight U-Net edge model with FP32 and INT8 deployment paths;
- event extraction from the pixel mask rather than full-image downlink;
- compact binary alert packets with integrity checks;
- a software study of persistent priority buffering and retry across missed
  contacts; and
- explicit evaluation of accuracy, data reduction, latency, and robustness.

So the distinctive goal is **transmitting information rather than raw
data**.

## Six-stage processing architecture

The project implements a dual-gate architecture around the validated
multispectral model; the LWIR-specific calibration path remains a
payload-dependent extension.

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 1. Gate 1 — Input quality screening                                      │
│    Shape/finite checks, dead bands/columns, saturation; optional          │
│    isolated-saturated-pixel scrub and optional dead-column repair         │
│    (both off by default)                                                  │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ 2. Sensor-dependent conditioning                                          │
│    Current model: fixed DN → TOA-reflectance rescaling (no sun correction)│
│    Future LWIR path: radiometric calibration, NUC, simulated-raw checks   │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ 3. Lightweight neural segmentation                                        │
│    Tiny U-Net, 482,737 parameters, ONNX FP32/INT8                         │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ 4. Temperature scaling and decision threshold                             │
│    p = sigmoid(z/T); threshold chosen on validation under recall/FAR      │
│    constraints (T = 2.12, τ = 0.96)                                       │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ 5. Event extraction                                                       │
│    Connected components, centroid/area/box/confidence/contrast features   │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ 6. Gate 2 and packet encoding                                             │
│    Output-sanity checks (valid probabilities, box geometry, area > 0),    │
│    version-3 binary packet with CRC32                                     │
└──────────────────────────────────────────────────────────────────────────┘
```

A persistent, priority-based downlink queue is evaluated separately as a
software study (see below); it is not one of the six per-tile inference stages.

The architecture dossier is available at
[`docs/MODEL_ARCHITECTURE.md`](docs/MODEL_ARCHITECTURE.md).

## What the experiments established

### Band selection from paper and empirical result

The band-information probe scored each band's local anomaly (pixel minus its
31×31 local mean) as a single-feature fire detector against the Pereira voting
masks. The masks are much more closely aligned with the reflectance/SWIR inputs
than with B10 thermal input:

| Band | Role | Pixel-level AUC (local anomaly) |
| --- | --- | ---: |
| C7 / SWIR2 | Strong active-fire signal | **0.993** |
| B10 / thermal infrared | Thermal control | **0.865** |
| C6 / SWIR1 | Supporting spectral contrast | **0.820** |
| C2 / Blue | Supporting context | **0.565** |

This supports the selection of [Pereira-3C](https://www.sciencedirect.com/science/article/abs/pii/S092427162100160X)
as the primary configuration for **this benchmark**; the paper describes the
three-band choice in detail. A single-band C7 anomaly rule reaches only pixel
F1 0.64: most of the gain to 0.95 comes from the learned multi-band spatial
model.

*Cross-band correlation provides sensor context; the AUC values above are the basis for the input-band selection.*

### Model results

The following values come from the final training and evaluation workflow in
[`notebooks/03_SPACETOON_IASTAM_MODEL_PROTOTYPE_PHASE3.ipynb`](notebooks/03_SPACETOON_IASTAM_MODEL_PROTOTYPE_PHASE3.ipynb)
(4,781 held-out test tiles; 20 epochs each; one run per configuration, seed 42).
They are reported against the Pereira voting-mask reference, which is an
algorithmic consensus and not field ground truth for a flight sensor.

| Configuration | Input | Precision | Recall | IoU | F1 | Frame recall | Frame FAR | Event recall |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **Pereira-3C** | C7+C6+C2 | **0.9496** | **0.9489** | **0.9034** | **0.9492** | 0.9648 | 0.0635 | **0.9553** |
| B10 control | B10 only | 0.5534 | 0.3280 | 0.2593 | 0.4119 | 0.1802 | 0.0263 | 0.1326 |
| Hybrid control | C7+C6+C2+B10 | 0.9663 | 0.9263 | 0.8973 | 0.9459 | 0.9643 | 0.0671 | 0.9455 |

Frame recall = fraction of voting-fire tiles with at least one predicted fire
pixel (Pereira-3C: 3,807 / 3,946, 95% CI 95.9–97.0%). Frame FAR = fraction of
"voting-zero" tiles that raised an alarm (53 / 835, 95% CI 4.9–8.2%). Event
metrics use a 3-pixel matching tolerance. Pereira-3C event recall is 0.946 for
reference events of 1–5 pixels and 1.000 above 5 pixels. With one training run
per configuration, the 0.003 F1 gap between Pereira-3C and the hybrid should
not be read as a demonstrated difference.

<p align="center">
  <img src="reports/figures/africa_thermal_contrast.png" alt="Band 10 thermal background distributions for North Africa and Sub-Saharan Africa" width="100%" />
</p>

*The thermal-background distributions illustrate why B10-only interpretation
must account for regional background conditions. This figure is contextual; the
configuration table above reports the segmentation results.*

An independent manual-label zero-shot test (100 human-annotated frames from 10
scenes, none of them in the training inventory) reports **F1 = 0.8493**, recall
**0.9590** and precision **0.7622** for Pereira-3C (B10-only: F1 0.3985; hybrid:
F1 0.8898). This is a useful circularity check because the training masks were
generated by reflectance-band algorithms. The model keeps its recall but marks
more pixels than the annotators did. All 100 frames contain fire, so no frame
false-alarm rate can be computed on this set.

### What the benchmark does not measure

- The benchmark tiles labelled "fire-free" (835 in the test split) are mostly
  tiles where **exactly one** of the three SWIR algorithms fired and the
  two-of-three vote failed (5,138 of 5,229 across the dataset), not empty
  scenes. The 6.3% frame false-alarm rate is a disagreement-with-consensus rate
  on hard tiles; the rate on genuinely empty scenes is unknown.
- The test split is 82.5% fire-positive and all scenes were acquired between
  6 and 30 August 2020 (Africa subset). Alert counts, alert precision and the
  data-reduction ratio below depend on fire prevalence; see
  [`docs/MODEL_ARCHITECTURE.md`](docs/MODEL_ARCHITECTURE.md) §12.4.

### Deployment and robustness results

- Tiny U-Net: **482,737 parameters**, 2.32 GMAC per 256×256×3 tile.
- INT8 model: **514.8 KiB** (527,200 bytes) versus 1.85 MiB for FP32. INT8
  agrees with PyTorch FP32 on 99% of frame-level alert decisions (pixel F1
  0.9482 vs 0.9489).
- End-to-end host benchmark (Intel Xeon 2.0 GHz, INT8, one thread): mean
  **65.7 ms**, **64.4 ms p50**, **77.7 ms p95**, 91.3 ms p99; inference is 88% of
  the total. On this host INT8 is *slower* than FP32 (model-only 55 vs 46 ms at
  one thread): its demonstrated benefit is size, not speed.
- These latency values are from an x86 host. They are **not** Raspberry Pi or
  flight measurements yet.
- Under a synthetic transient stress test (20 saturated pixels injected per
  frame), Gate 1 scrubbing recovered pixel F1 from **0.67 to 0.94** and frame
  FAR from 1.00 to 0.07. Scrubbing costs about 1.5 points of pixel recall on
  clean data (real one-pixel fires can saturate), so it is **off by default**.
  Dead columns remain highly damaging (one dead column in one band raises frame
  FAR to 0.36): in the evaluated configuration Gate 1 flags them but does not
  repair them (the demo has an optional interpolation repair, off by default and
  not yet measured). These are synthetic perturbations, not radiation tests.
- In the 50%-capacity queue simulation, priority plus persistence/retry
  delivered **87.6%** of the top-20% urgent events, compared with **33.6%** for
  FIFO, with zero permanently lost packets for the persistent policies. Under
  that capacity the priority policy delivers 23.5% of all packets within 48 h
  (the rest remain queued), and "top-20% urgent" is defined by the same urgency
  score that orders the queue.

## <i class="fa-solid fa-box-archive" style="color:#38bdf8; font-size:1.05em; vertical-align:-1px; margin-right:8px;"></i> Information product and downlink reduction

For the current three-band, 256×256, 16-bit input tile:

```text
3 × 256 × 256 × 2 bytes = 393,216 bytes raw
```

The packet protocol (version 3, custom binary format) extracts events rather
than compressing the full image:

- **48 bytes** for a single-event alert (17 B header + 27 B event + 4 B CRC);
- up to **183 bytes** for the documented six-event packet;
- **21 bytes** for a fire-free heartbeat (sent on the first frame and every 30th);
- CRC32-protected binary fields include frame ID, event count, coordinates,
  pixel box, area, confidence, contrast, and status flags. Landsat patches carry
  no acquisition time, so the timestamp field is zero and flagged "time
  unavailable".

The corresponding ratios are **8,192×** for a 48-byte single-event packet and
**2,148.7×** for the 183-byte worst-case packet. The reported aggregate
accounting result is **6,234.99×** over 1,500 randomly drawn test frames
including heartbeats; **82% of those frames produced an alert**, so this is a
fire-heavy sample (5,132× per alert packet). For other fire prevalences the
ratio is higher but the share of alerts that are real fires drops sharply
unless the false-alarm rate on empty scenes is far below 6% (projection in
[`docs/MODEL_ARCHITECTURE.md`](docs/MODEL_ARCHITECTURE.md) §12.4). These are
software/accounting results, not measured RF-link throughput.

Known packet limits: area is stored in 0.1 ha units, so in the evaluated notebook
run a single pixel rounds to zero below about 22 m ground sampling and Gate 2
then rejects it (the demo floors the field at 1). Events beyond six per frame are
not transmitted; the demo records how many were dropped (saturating at 15) in
the event flags byte, with the packet layout and the 183-byte maximum unchanged.
The packet is a custom format, not a CCSDS Space Packet.

The persistent queue keeps an alert for a later contact when the current
contact is missed. This behavior is simulated in software with synthetic
arrivals and contact outcomes (lost contact 25%, link cut 25%, normal 50%);
orbital contact geometry, queue-storage limits and a flight communications
subsystem are outside the current scope.

## <i class="fa-solid fa-terminal" style="color:#38bdf8; font-size:1.05em; vertical-align:-1px; margin-right:8px;"></i> Interactive web demo

The Gradio demo makes the software pipeline inspectable for development and
defense. It accepts real Landsat-8 GeoTIFF patches and displays the input,
segmentation output, extracted events, packet fields, and reduction statistics.

<p align="center">
  <img src="img/demo_interface.gif" alt="Thermal-Edge-Fire web demo" width="100%" />
</p>

The demo includes:

- SWIR2/SWIR1/Blue false-color visualization and segmentation;
- Gate 1 quality checks and an optional transient-scrub toggle;
- event clustering and compact packet inspection;
- CRC and packet-field decoding;
- FP32/INT8 parity and host latency benchmarking; and
- bundled golden vectors for reproducibility checks.

The bundled models are Pereira-3C only (FP32 and INT8); the B10-only and hybrid
results are evaluation results, not runnable demo models. The demo's threshold
slider changes the operating point away from the benchmark value (0.96).

The demo is an engineering demonstrator. Its results should not be presented
as a live spacecraft or as a substitute for target-board validation.

## Quickstart

### Local environment

```bash
git clone https://github.com/kacemamine721-star/thermal-edge-fire.git
cd thermal-edge-fire
pip install -r requirements.txt
pytest -v
```

### Launch the web demo

```bash
cd demo
pip install -r requirements.txt
python app.py
# Open http://127.0.0.1:7860
`````

Demo verification tests (packet encoding and CRC, Gate 1, event metrics, INT8/FP32
agreement, golden vectors; tests that need a missing model or sample are skipped):

```bash
cd demo
python test_demo.py
```

### Run with Docker

```bash
docker build -t iastam-edge-demo demo/
docker run -p 7860:7860 --memory="512m" --cpus="1.0" iastam-edge-demo
```

The Docker resource limits are reproducibility settings for the demo; they do
not constitute a measured spacecraft power budget.

## Dataset and validation strategy

| Dataset or source | Role | Scope |
| --- | --- | --- |
| Landsat-8 ActiveFire / Pereira et al., Africa subset | Primary training, validation and test reference | 27,729 patches (256×256, 30 m) from 514 parent scenes, split by scene 360 / 77 / 77 (seed 42); no WRS-2 path/row shared between splits; all acquired 6–30 Aug 2020. Voting masks (≥ 2 of 3 algorithms) are reflectance/SWIR-derived |
| Pereira manual fire annotations | Zero-shot check | 100 human-annotated frames from 10 scenes, all containing fire; absent from the training inventory. Used to assess circularity |
| TS-SatFire / VIIRS | Secondary cross-sensor study | Planned comparison and temporal/domain-transfer work |
| Simulated-raw LWIR and THRawS-style data | Future payload validation | Required to quantify the real-versus-simulated sensor gap |

The validation set is split by scene into a calibration half (fits the
temperature) and a selection half (chooses the epoch and threshold); the test
split was evaluated once, after selection.

The final LWIR path requires labels generated from thermal-native information,
such as MODIS/VIIRS thermal fire products or a validated brightness-temperature
procedure. The current Pereira-3C score cannot be transferred to that path
without this additional validation.

## Roadmap and known boundaries

1. Measure the frame false-alarm rate and alert precision on genuinely empty,
   orbit-like scenes, and report data reduction at realistic fire prevalences.
2. Train and evaluate a model with LWIR-native labels rather than treating the
   B10 control as flight validation.
3. Add and quantify the microbolometer-specific raw-data path: radiometric
   calibration, two-point NUC, optical blur, noise, quantization, and resampling.
4. Run the ONNX/INT8 bundle on Raspberry Pi CM4-class or equivalent hardware
   and measure latency, memory, and energy per inference.
5. Measure the optional dead-column repair (implemented in the demo, not yet
   evaluated) on the robustness scenarios, and add a transient filter that does
   not delete real one-pixel fires.
6. Complete hardware-in-the-loop validation for sensor faults, radiation-like
   transients, missed contacts, queue overflow, and retry behavior.
7. Add orbit/contact simulation and validate downlink performance against an
   actual communications budget.

Until those steps are complete, the defensible description is: **a validated
software information-extraction pipeline on Landsat/Pereira data and a proposed
6U-class deployment architecture, with LWIR as an unvalidated payload path**.
